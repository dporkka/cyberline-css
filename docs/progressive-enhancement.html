Progressive enhancement and document rendering

Syntyr's default contract is HTML first. Core CSS doesn't include JavaScript, network requests, icons, fonts or a client-side build step. Progressive enhancement should add polish and optional interactions to working baseline workflows.

For a static showcase of search, figure, mark, kbd, output, meter and safe code overflow with zero scripts, see native-elements.html. The example is presentational, not a working search service.

Native actions and server responses come first

Always use anchors for navigation, buttons for actions, associated labels for controls, and native form submission where the application has a server endpoint. A GET form below remains usable without HTMX, React, or other client JavaScript:

<form action="/customers" method="get" role="search">
  <label for="q">Search customers</label>
  <input id="q" name="q" type="search" required>
  <button type="submit" class="syn-button syn-button--primary">Search</button>
</form>

HTMX or other adapters can enhance the same form. Return safe server-rendered HTML; handle validation and permissions on the server. If the enhancement fails, the form still navigates to the server search result. The host owns those routes.

Native details is appropriate for disclosure. For a modal preview, include a real navigation route for critical information because commandfor and command="show-modal" are not universally supported in older browsers:

<a href="/reports/quarterly">Read full report</a>
<button type="button" commandfor="report-preview" command="show-modal">
  Preview report
</button>
<dialog id="report-preview" aria-labelledby="report-preview-title">
  <h2 id="report-preview-title">Report preview</h2>
  <p>Illustrative summary. The full report link works in every browser.</p>
  <form method="dialog"><button>Close</button></form>
</dialog>

Don't rely on ARIA to implement state changes or disable interactions. Use native control semantics; any optional JavaScript must feature-detect browser support, preserve keyboard focus, and never hide the only path to important data.

Built-in system-aware theme

Load core and set data-syn-theme="auto". No separate automatic theme stylesheet is needed:

<link rel="stylesheet" href="/css/syntyr.core.css">
<main class="syn-root" data-syn-theme="auto">...</main>

auto uses the Grid palette for dark system preferences and Studio for light. It works on both root and nested themed regions, requires zero JavaScript, and does not override a user's explicitly selected grid, noir, or studio theme. Host apps can change the attribute if they provide a theme picker. Automatic themes use the native light-dark() CSS feature with a compatible fallback; existing tests verify that the palette stays aligned with Grid and Studio.

RTL, mixed-direction data and translated content

Syntyr inherits the document's native lang and dir attributes. Its classed and opt-in semantic tables align to the inline start; explicitly numeric .syn-cell--numeric cells align to the inline end. Timeline markers, decorative panel cuts, and native popover fallbacks follow logical directions. No RTL-only bundle or JavaScript is required.

<main class="syn-root syn-semantic" lang="ar" dir="rtl" data-syn-theme="studio">
  <h1>لوحة التحكم</h1>
  <p>رمز الأصل: <bdi dir="ltr">ACME-1029</bdi></p>
  <table>
    <thead><tr><th scope="col">الأصل</th><th scope="col">الحالة</th></tr></thead>
    <tbody><tr><td>لوحة رقم ١</td><td>نشط</td></tr></tbody>
  </table>
</main>

Set dir on the actual text container, not on a Syntyr theme selector. Use bdi or an explicit dir="ltr" wrapper for identifiers, URLs, and mixed-language snippets. The host application owns translations, locale formatting, input validation and accessible names; CSS cannot translate text. Direction-aware numeric alignment intentionally differs from physically right-aligned LTR amounts. Consumers needing fixed geographic or numeric conventions should explicitly style those application-specific columns.

The offline Arabic/English/German fixture includes a native and classed table, long translated form labels, dir="ltr" content nested inside an RTL page, activity timeline, and native popover. It is illustrative: form navigation does not save any data.

Development-only regression checks:

python3 -m unittest discover -s tests -p test_rtl_contract.py -v
python3 tests/rtl_browser.py --browsers chromium firefox webkit

The RTL page is also included in the optional browser, reflow and axe audit inventories. Browser viewport tests do not establish actual 200% or 400% browser zoom, screen-reader interoperability, or WCAG conformance. If an engine cannot launch, report it as blocked rather than passing it.

Opt-in print styling

Load syntyr.print.css after core when printing reports or invoices:

<link rel="stylesheet" href="/css/syntyr.core.css">
<link rel="stylesheet" href="/css/syntyr.print.css">

It uses a readable light palette on paper, drops decorative backgrounds and shadows, and expands overflow regions. Use .syn-print-hide only on genuinely nonessential controls. The app must still ensure that its server-rendered data is complete, because CSS cannot materialize unloaded or virtualized rows.

Responsive, legible, and fast

  • .syn-layout now uses intrinsic auto-fit tracks. It adapts to the width of its actual host, not only the viewport; narrow embedded panels stack.
  • The current design uses scalable typography tokens; small labels use --syn-type-sm and optional metadata styles can be tuned by consumers. Preserve user font scaling and test 200% and 400% genuine browser zoom.
  • Core never requires a polyfill. Load optional stylesheets only when their capabilities are needed, or use syntyr.all.css for demos.
  • Scoped semantic file inputs use min-inline-size: 0 so browser-native file pickers can shrink in a grid or narrow card without causing page-wide horizontal overflow. Test translated picker labels in each target browser.
  • Reduced motion, forced colors and assistive-technology behavior still need manual, representative real-device verification. Automated checks alone cannot establish WCAG compliance.

Cross-engine regression verification

The development-only tests/progressive_browser.py checks computed theme colors, nested opt-in themes, semantic-mode isolation, narrow embedded layout, print-safe readable data, and disabled print motion in real browser engines:

python3 tests/progressive_browser.py --browsers chromium firefox webkit

It requires Playwright and installed browser binaries for development only. For a host without WebKit libraries, use an official matching Playwright container. The test fails visibly if a browser cannot launch; it never counts unexecuted engines as passing. Run accessibility and reflow suites separately.

Limitations: Playwright viewport/root-font stress tests do not establish real browser UI zoom at 200%/400%. CSS zoom and CDP page scale are not interchangeable with native browser zoom: page scale may be post-layout. Real OS high-contrast and assistive-technology testing must be done manually.
